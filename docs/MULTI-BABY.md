# 多宝宝设计（P5.1）

> 状态：**已确认并实现（2026-11-07）**。确认结果见第 9 节；P5.2 已落地（迁移、切换、按宝宝隔离、同步）。
> 前置：P4 已完成（`docs/SYNC.md`），同步已在跑；P5 不能破坏已有的同步与旧备份兼容。

## 1. 目标与边界

**要解决的事**：双胞胎、二胎时，两个宝宝各自有一份资料、照护记录、接种、里程碑、生长曲线，切换着看。

**不做的事**：

- 不做多宝宝对比视图（同一天的喂奶次数并排之类）。
- 不做「一条记录同时属于两个宝宝」——记录永远只属于一个宝宝。
- 不做按宝宝的同步权限、邀请或共享。一把家庭密钥同步全部宝宝。
- 不做宝宝档案的合并/拆分。

## 2. 数据结构

### 2.1 宝宝档案

```ts
interface BabyProfile {
  id: string;                 // 新增：稳定标识，记录靠它归属
  name: string;
  birthDate: string;
  sex?: "male" | "female";
  dueDate?: string;
  /** 新增：这个宝宝自己的疫苗计划与里程碑，从顶层搬进来。 */
  vaccinePlan?: VaccinePlan;
  milestones?: Record<string, string>;
}
```

`Workspace` 改为：

```ts
interface Workspace {
  schemaVersion: 1;           // 不变，新字段全部可选
  profiles: BabyProfile[];
  activeProfileId: string;
  // baby 迁移后删除，不再读写
  // vaccinePlan、milestones 迁移进各自的 profile，不再读写
  ...
}
```

### 2.2 记录归属

`GrowthEntry`、`VaccinationRecord`、`Recap`、`MediaAsset`、`Candidate` 都加可选 `babyId?: string`。

- 旧数据迁移时补成唯一的宝宝；之后新记录写入 `activeProfileId`。
- `booking`/候选没有 `babyId` 的视为「待归到当前宝宝」——只发生在旧备份导入的中间状态。
- 回顾（`Recap`）按条目归属：一条回顾只能引用同一宝宝下的记录，创建时已按当前宝宝过滤。

### 2.3 为什么把疫苗计划与里程碑放进档案

它们本来就是「某个宝宝的」数据，留在顶层就得再加一层 `按 babyId 的映射`，读的时候多一次查表，还要处理「activeProfile 不存在对应键」的兜底。放进档案后，组件拿到的仍是同一个 `Record<string, string>` / `VaccinePlan`，App 只换数据来源。

## 3. 迁移（可单独上线）

新增 `domain/profiles.ts` 的 `migrateProfiles(workspace, idFactory)`：

1. 已有 `profiles` 且 `activeProfileId` 合法 → 直接返回，幂等。
2. 否则把顶层 `baby` 包装成 `{ ...baby, id: idFactory() }`，`vaccinePlan`、`milestones` 搬进这个档案。
3. 给所有没有 `babyId` 的 `entries` / `vaccinations` / `recaps` / `media` / `candidates` 补上这个 id。
4. `activeProfileId` 设为唯一的宝宝；删除顶层 `baby` / `vaccinePlan` / `milestones`。

调用点与 P4.2 的 `migrateSyncMeta` 相同：`load()` 读入本机数据、`restore()` 导入备份时各跑一次。旧备份（无 `profiles`）照常导入；新备份（有 `profiles`）校验接受两者之一。

**兼容窗口**：旧版 `isWorkspace` 要求顶层 `baby` 存在（`workspace-schema.ts:46`），迁移后它消失，旧代码打开会报「本机数据格式暂不支持」，数据仍在 IndexedDB 里但界面上读不出来。两个选项：

- **A 保留镜像**：顶层再留一份 `baby`，每次写档案时同步更新成当前宝宝。旧代码能打开，但旧界面没有按宝宝过滤，会把几个宝宝的记录混在一起显示；好处是回滚不用先导出。
- **B 不做镜像**：单一数据源，结构干净。回滚路径只有「导出当前宝宝旧格式 → 换回旧代码 → 恢复备份」，且必须在升级前先导出。

建议 B：镜像是一份要时刻同步的重复数据（`数据泥团`），日常维护成本高于它偶尔救急的价值；回滚是罕见操作，导出一次就能解决。

## 4. 界面

- **切换入口**：顶部「宝宝的今天」标题旁加下拉（头像/名字），列出全部宝宝 + 「添加宝宝」。切换只改 `activeProfileId`，本机持久化，不重载页面。
- **按宝宝过滤**：今天页、时间线、趋势、健康（疫苗/生长曲线/里程碑）、回顾、待整理都只显示 `babyId === activeProfileId` 的记录；没标注的旧记录在迁移时已补齐，不会漏。
- **添加/编辑宝宝**：家庭页现有的昵称/生日/性别/预产期表单改为「当前宝宝」，另加「添加宝宝」「删除宝宝」。
- **删除宝宝**：二次确认，说明会隐藏（墓碑同步）该宝宝的全部记录；不是物理删除，另一个设备同步后同样看不到。最后一个宝宝不能删。

## 5. 统计与领域函数

- `stats`、`sleep`、`feeding`、`summary`、`milestones`、`growth` 等纯函数签名不变，调用方先按 `babyId` 过滤再传入。
- 「今日照护」「下次喂奶参考」「交接摘要」都只算当前宝宝。
- 月龄、疫苗推算、生长曲线本来就以 `profile` 为输入，切换到当前宝宝即可。

## 6. 同步（P4 的延伸）

- `singletons.baby` 改为 `singletons.profiles`，值是一个数组（服务端 `SINGLETONS` 白名单加 `profiles`，删掉 `baby`）。档案内的 `vaccinePlan` / `milestones` 随档案整体覆盖，冲突规则同 P4（后写者胜）。
- 记录 payload 自带 `babyId`，服务端不用改表。
- `activeProfileId` 是设备偏好，**不进同步**：两个人各看各的当前宝宝，互不干扰。
- 墓碑按条目走，删除宝宝时给它的全部记录写墓碑（沿用 `stampChanges`，只是批量）。
- 老客户端（P4 版本）与新服务端之间：`baby` 键不再被接受/下发，老客户端会同步失败——所以 P5 上线要求所有设备一起更新，或者服务端同时接受 `baby` 与 `profiles` 一段时间（见第 9 节问题 3）。

## 7. 测试计划

自动化：

1. 旧 workspace（无 `profiles`）迁移后：一个宝宝、id 稳定、全部记录带 `babyId`、计划与里程碑搬进档案、幂等。
2. 旧备份导入 → 迁移 → 导出新备份 → 再导入，结构与数据一致。
3. 两个宝宝各自记录：时间线/统计/疫苗/生长曲线只出现当前宝宝的。
4. 同步：A 加宝宝、B 拉到；A 切宝宝只改本机偏好，B 不受影响；A 删宝宝 → B 同步后隐藏。
5. 旧格式单宝宝导出 → 能用旧版前端打开。

手动：顶部切换在 375/320px 下不溢出；切换后今天页数字即时变化；删除宝宝有二次确认且不可删到 0 个。

## 8. 回滚

- **关功能**：切换回「只有一个宝宝」即与现在一致；多出来的宝宝可以在界面上删掉（写墓碑同步）。
- **导旧格式**：家庭页「导出备份」增加「导出当前宝宝（旧版格式）」，输出 v1 结构（`baby` + 该宝宝的记录），旧版前端可直接恢复。适合想退回 P4 版本时用。
- **数据结构**：`schemaVersion` 保持 1，新字段全部可选；但没有 `baby` 的旧版前端能否打开需要先验证（第 3 节）。

## 9. 需要你确认

1. **疫苗计划与里程碑放进宝宝档案**（第 2.3 节），而不是顶层按 id 分表——接受吗？
2. **切换入口放顶部标题旁**（不改底部导航），可以吗？还是要放家庭页？
3. **旧版兼容**（第 3 节）：选 B（不留顶层 `baby` 镜像，回滚靠导出）可以吗？
4. **同步切换**：P5 上线时要求所有设备一起更新（简单，服务端不兼容 `baby`），还是服务端同时接受 `baby` 与 `profiles` 一段时间（多一段兼容代码，老设备不会突然同步失败）？
5. **删除宝宝**按「墓碑隐藏、可同步、最后一个不能删」处理，符合预期吗？还是希望能彻底清掉、不占同步空间？
6. **导出当前宝宝的旧格式**作为回滚路径，够用吗？

**确认结果（2026-11-07）**：

1. 疫苗计划与里程碑放进宝宝档案：接受。
2. 切换入口放顶部标题行（`#profile-select`），不改底部导航。
3. 不留顶层 `baby` 镜像，回滚靠「导出当前宝宝的旧格式」。
4. 同步不留兼容期，要求所有设备一起更新；服务端 `singletons` 只认 `profiles`。
5. 删除宝宝按墓碑隐藏、可同步、最后一个不能删。
6. 导出当前宝宝旧格式作为回滚路径：够用。

**实现补充**：旧结构迁出的宝宝用固定 id `default`（两台设备各自升级后记录能合并到同一档案）；新加的宝宝用随机 id；`activeProfileId` 只存本机、不进同步。
